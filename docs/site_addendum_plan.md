# Plan: site addendum (map, work types, model's role, features, style)

Everything is backed by code already in `src/` and `api/`. `src/` is not
touched. `api/` gains fields and two small read-only endpoints, plus two
committed data artefacts distilled once from the repo's own data so the deploy
has no dependency on the gitignored `data/`. Copy follows the main rules: no em
dashes, plain words, every term explained once.

## 1. API changes (all additive)

### `POST /api/plan` and `POST /api/chat` response, new per-hour and summary fields

```jsonc
"hours": [{
  ...existing...,
  "wbgt_lo": 30.1, "wbgt_hi": 34.8,        // p10..p90 forecast band for this hour and lead
  "uncertain": true,                        // the band straddles 32.1 C
  "reactive_work_fraction": 0.0,            // the stop-when-hot rule (policy_reactive)
  "retained_load_reactive": 12.4,
  "cycle": "work 45 min, rest 15 in shade"  // plain per-hour instruction from the work fraction
}],
"summary": {
  ...existing...,
  "peak_reactive": 8.3, "tail_reactive": 15.9,
  "pct_peak_reduction_vs_reactive": 16.8
},
"meta": {
  ...existing...,
  "lead_days": 1,
  "forecast_run": "2026-09-10T00:00Z model run",
  "uncertainty_note": "The forecast band is p10 to p90 from analog resampling of past forecast errors at this lead.",
  "wide_band": false,                       // true beyond lead 3 -> "less certain this far out"
  "dry_hot_day": false,
  "dry_hot_note": "This day looks dry and hot. WBGT can under-read the strain when the air is very dry. Water and rest still matter."
}
```

- **Band**: `api/planning.py` widens the point forecast per hour with residual
  quantiles from `api/data/wbgt_residuals.json` (below). The plan itself stays
  on the point forecast, which technical_report section 15 shows is the right
  choice at these leads. `uncertain` is `wbgt_lo <= 32.1 <= wbgt_hi`.
- **Reactive series**: `src.scheduler.policy_reactive(wbgt_point, allowed,
  w_req)` on the same hours, retained-load path re-derived the same way as the
  plan and the calendar ban.
- **`cycle`**: snap the continuous work fraction to the nearest ACGIH cycle
  (1.00 full hour, 0.75 = 45/15, 0.50 = 30/30, 0.25 = 15/45, 0 = rest in
  shade) for the sentence; the exact percentage is still in
  `plan_work_fraction`.
- **`dry_hot_day`**: warm-season day where the local 10:00 to 16:00 mean RH is
  below 25 percent, mean air temp above 40 C, and mean air temp minus mean
  WBGT above 12 C. Uses only fields already fetched. One caution line, no
  second number. Studies 7 and 11.

### `PATCH`-free "what I have" flow

`POST /api/chat` body gains an optional `intent` object. If present and valid,
the stream skips parsing and goes straight to plan and explain. The frontend
flow becomes: user message -> `POST /api/parse` -> if `clarification`, show the
one question; if `parsed`, show an editable "Here is what I have" card (each
field, its value, and its source: "from the map pin" for location when a pin
was set, otherwise "from your message") -> user edits and confirms -> `POST
/api/chat` with the confirmed `intent` -> streams the explanation and the
artifact. Anything still missing that affects safety is asked as one question;
the "used to the heat" state is never inferred silently.

### `GET /api/replay` and `GET /api/replay/{slug}`

Serves `api/data/replay/{slug}.json`: a real past 7-day stretch, each day
planned walk-forward on information available before it, with the realised
WBGT, the plan, the calendar ban, the reactive rule, and per-day peak and
tail. First pass ships one week, the hottest 7-day run in the 16-year record,
labelled "simulated on real past weather, no future data used". `GET
/api/replay` lists available slugs.

### Committed data artefacts

- `scripts/build_residual_table.py` -> `api/data/wbgt_residuals.json`
  (~2 KB): per local hour and lead (1, 2, 3), the p05/p10/p50/p90/p95 of
  `true minus forecast` WBGT, from `data/doha_forecast_archive.csv` and
  `data/doha_wbgt_16yr.csv`. Run once, committed, regenerated by `run_all.sh`.
- `scripts/build_replay_weeks.py` -> `api/data/replay/*.json`. Same inputs.

Both scripts are additive under `scripts/`. The API reads the JSON only.

## 2. Interactive map (item 1)

- **MapLibre GL JS** with **OpenFreeMap** vector tiles (no key, open data). A
  hand-written style JSON per theme built from the design tokens (land
  `--bg`, water a desaturated `--accent`-cool, roads `--border-strong`, labels
  `--text-secondary`). Lazy `import("maplibre-gl")` on mount only; never in the
  first-paint bundle, never on routes that do not show a map.
- **App input**: search or drop a pin sets `lat`/`lon` for `/api/plan` and
  `/api/chat`. Default view Doha. No sign in, no stored location.
- **Forecast cell**: the 0.25 degree cell the pin falls in, drawn as a light
  translucent square, labelled "The forecast covers this area, about 25 km
  across. It is not specific to one street or one trench."
- **Inland note** (cheap, optional): if the pin is more than ~20 km inland,
  one line, "Inland tends to read a little cooler on this index because the
  air is drier." One sentence, Study 9, no number.
- **Not the only input**: a text field that matches the preset list, manual
  lat and lon entry, and the pin is keyboard movable (arrow keys nudge it
  when the map has focus). Optional Nominatim search, keyless, debounced,
  degrades to "search is unavailable, use a preset or coordinates".
- **Reduced motion or low power**: no globe, no fly-to, the camera snaps.
- Loading, empty (no pin yet, Doha default shown), and error (tiles failed,
  fall back to the coordinate form) states.

## 3. Work types and acclimatisation (item 2)

Categories unchanged (`src/heat_stress.py`). Labels and examples, from the
activity descriptions in that file:

| value | label | one line |
|---|---|---|
| light | Light | standing, light hand or arm work, for example inspection or light assembly |
| moderate | Moderate | steady hand and leg work and walking, for example carrying light loads or plastering |
| heavy | Heavy | hard sustained effort, for example digging, shovelling, carrying heavy loads, pouring concrete |
| very_heavy | Very heavy | near maximal effort, for example breaking ground by hand or climbing stairs with a load |

"Used to the heat" toggle: label "Has the crew been working in this heat for
more than two weeks", one line, "A body that is not used to the heat is at
higher risk at the same conditions."

## 5. Style, first pass

- **a headline number**: every artifact leads with one line, large, stated
  once, for example "Worst point of the day: heat load 6.9, down from 8.0
  under the fixed rule, same hours worked."
- **b direct annotations**: labels on the curve in place, "Forecast peak,
  about 2 pm", "The fixed rule works the crew until here", "The plan rests
  through the three hottest hours".
- **c landing is one chart, four reveals**: the same Doha-today day chart
  builds as the visitor scrolls: bare forecast, then the 32.1 C line, then the
  fixed rule, then the plan. The highest-craft element on the site.
- **d live-now marker**: when the shown day is today, a thin vertical line at
  the current local time, updating.
- **e loading that teaches**: the four real steps shown in sequence while a
  plan computes, driven by the existing `status` frames.
- **f never blank**: a faded example artifact for Doha today before the first
  request.
- **g two themes with intent**: dark is the night-shift view and primary;
  light is a daytime operations room, warm and paper-like; the WBGT ramp is
  already tuned per theme; numbers stay tabular and lining in both.
- **h motion budget**: one shader hero; everything else transform and opacity,
  <= 400 ms, eased; offscreen pauses; count-ups settle; all off under reduced
  motion or Save-Data. Written into DESIGN.md.
- **i share image per plan**: `app/opengraph-image.tsx` becomes dynamic,
  reading the same `q` params, rendering the annotated chart plus the headline
  number.
